## 1. Порядок байтов

Allegrex работает в **little-endian** режиме (Config.LEL). ELF-образы PSP —
MIPSEL (`EI_DATA = ELFDATA2LSB`). Следовательно и данные, и выборка инструкций
little-endian.

> Проект исторически использовал big-endian в `Memory` при том, что загрузчик
> читал MIPSEL. Это взаимно противоречиво. Исправлено в пользу little-endian.

## 2. VFPU: раскладка полей

Из `MIPSVFPUUtils.h` (PPSSPP master), дословно:

```c
#define _VD (op & 0x7F)         // приёмник,      биты 6..0
#define _VS ((op>>8) & 0x7F)    // источник 1,    биты 14..8
#define _VT ((op>>16) & 0x7F)   // источник 2,    биты 22..16
```

**Все три поля по 7 бит** (регистры 0..127). Биты 15 и 7 НЕ входят в поля
регистров — они несут размер вектора:

`GetVecSize()` / `VSuff()` (PPSSPP):

```c
int a = (op>>7)&1;    // бит 7  — младший бит размера
int b = (op>>15)&1;   // бит 15 — старший бит размера
a += (b<<1);
// 0 = .s (1 lane), 1 = .p (2), 2 = .t (3), 3 = .q (4)
```

Это совпадает с официальной таблицей Hitmen: `vadd.s` = `0x60000000`,
`vadd.p` = `0x60000080` (бит 7), `vadd.t` = `0x60008000` (бит 15),
`vadd.q` = `0x60008080`.

## 3. VFPU: опкоды

VFPU **не** живёт целиком в COP2 (0x12). Ключ выбирается по опкоду MIPS
(биты 31..26) и под-индексу:

| Опкод | Под-индекс | Таблица | Поддерживаемые сейчас |
|-------|-------------|---------|------------------------|
| `0x18` `011000` | биты 25..23 | `tableVFPU0[8]` | 0=vadd, 1=vsub, 7=vdiv |
| `0x19` `011001` | биты 25..23 | `tableVFPU1[8]` | 0=vmul |
| `0x1B` `011011` | биты 25..23 | `tableVFPU3[8]` | 2=vmin, 3=vmax |
| `0x34` `110100` | биты 25..21 | `tableVFPU4Jump[32]` | → `tableVFPU4` |
| `0x34`, биты 25..21 == 0 | биты 20..16 | `tableVFPU4[32]` | 0=vmov, 1=vabs, 2=vneg |
| `0x12` `010010` | биты 25..21 | `tableCop2[32]` | lv.s, sv.s, mftv, cfti … |

Контрольные слова (`tableVFPU*` + Hitmen), все поля регистров нулевые:

```
vadd.s 0x60000000   vsub.s 0x60800000   vdiv.s 0x63800000
vmul.s 0x64000000   vmin.s 0x6D000000   vmax.s 0x6D800000
vmov   0xD0000000   vabs.s 0xD0010000   vneg.s 0xD0020000
```

Следствия, важные для декодера:

* источник 1 — **биты 14..8**, а НЕ 21..25 (как в обычном R-type);
* источник 2 — **биты 22..16**;
* приёмник — **биты 6..0**;
* бит 7 и бит 15 зарезервированы под размер вектора и **обнуляются**
  при извлечении регистра;
* поле размера вектора не совпадает с `fmt = word & 0x3F`.

## 4. CP0 (Hitmen, MIPS32 Vol. III)

| Рег | Имя | Примечание |
|-----|-----|------------|
| 8 | BadVAddr | |
| 9 | Count | |
| 11 | Compare | |
| 12 | **Status** | |
| 13 | **Cause** | |
| 14 | **EPC** | |
| 15 | PRId | |
| 16 | Config | |
| 25 | **EBase** | база векторов исключений |
| 30 | ErrorEPC | |

**Отдельного регистра Interrupt Mask на Allegrex нет.** Маска прерываний —
поле **IM в Status, биты 15..8** (8 линий, по 1 биту на линию).

Status (MIPS32):
```
bit 0     IE      Interrupt Enable
bit 1     EXL     Exception Level
bit 2     ERL     Error Level
bit 22    BE      Boot Exception
bits15..8 IM[7:0] Interrupt Mask
```

Cause (MIPS32):
```
bits 6..2 ExcCode
bit  31    BD      Branch Delay
bits15..10 IP[5:0]
```
Линии прерывания PSP выделены в Cause биты 8..15 (8 линий), что согласуется
с 8 битами IM в Status и со схемой векторов ниже.

## 5. Векторы исключений

Формула MIPS32:

```
General:  vector = EBase + 0x100 + ExcCode * 0x20
Interrupt: vector = EBase + 0x100 + irq    * 0x20
```

Согласуется с Hitmen (`SC_TABLE`, `EXC_8_SYSCALL`, `EXC_31_ERROR`).

Коды исключений (Cause.ExcCode, биты 6..2), нужные проекту:

| ExcCode | Имя | Вектор при EBase=0 |
|---------|-----|---------------------|
| 0 | Int (прерывание) | `0x100 + irq*0x20` |
| 4 | AdEL (ошибка адреса при чтении) | `0x180` |
| 5 | AdES (ошибка адреса при записи) | `0x1A0` |
| 8 | Sys (syscall) | `0x200` |
| 9 | Bp (break) | `0x220` |
| 10 | RI (недопустимая инструкция) | `0x240` |
| 12 | **Ov — Arithmetic Overflow** | `0x280` |

> В ранней редакции этого документа для переполнения был указан код 4 —
> это AdEL. Корректный код арифметического переполнения — **12** (Ov).

Именно поэтому адрес возврата при исключении кладётся в EPC вместе с BD=1:
инструкция находится в слоте задержки, поэтому EPC указывает на саму
инструкцию ветвления, а не на инструкцию в слоте.

### 5.1 Роль Status.BEV

MIPS32 Vol. III, Table 5-6: *«EBase register for exceptions that occur when
Status.BEV equals 0»*. То есть формула через EBase действует **только при
BEV = 0**. При BEV = 1 (загрузка; таблица векторов ещё не выставлена)
используются фиксированные загрузочные векторы:

```
общее исключение: 0x00000180      (0x80000180 при Status.BE = 1)
прерывание:        0x00000380 + irq * 0x20
```

То есть при BEV = 1 **все** общие исключения сходятся на одном адресе `0x180` —
именно в этом и смысл бита: один обработчик на весь загрузочный период.

Бит 31 Status (BE, Boot Exception) на PSP равен 0, так как Allegrex —
little-endian; используется младший адрес.

## 5.2 COP0: раскладка селектора операции

Две схемы встречаются в источниках, и реальный выбор зависит от кодировки,
которой пользуется гостевой код:

**Схема PPSSPP.** `Core/MIPS/MIPSTables.cpp`:
```c
{ MIPSOP_COP0, ... , 21, 5 }   // encodingBits[Cop0] = (21, 5)
```
`tableCop0` индексируется битами 25..21: `[0] = mfc0`, `[4] = mtc0`.
`Interpreter.cpp`, `Int_Cop0`:
```c
switch ((op >> 21) & 0x1f) {
case 0: // mfc0
case 4: // mtc0
```
→ селектор MF/MT в битах **25..21**.

**Схема MIPS32 Vol. III.** `rs` = 0, вид операции в битах **4..0**
(MF = 0b00000, CF = 0b00010, MT = 0b00100, CT = 0b00110).

Зарезервированное поле — биты **10..3** (между `rd` и `op`); они обязаны быть
нулевыми. Бит 25 (CO) = 1 означает сопроцессор 1 (`eret`, `wait`, `tlb*`),
а не регистры CPU.

Значения опкода 8..15 (бит 3 установлен) принадлежат `cache`, а не `cfc0`,
поэтому проверять подфункцию битов 2..0 отдельно не нужно: опкод CF — это
конкретное значение 2, а не «биты 4..3 = 01».

> Итог: `mtc0` записан словом `0x40886000` (rs5 = 4, младшие биты = 0) —
> это MTC0 по схеме PPSSPP, но MFC0 при наивном чтении битов 4..0.
> Реализация принимает обе схемы и отвергает всё, что не соответствует
> ни одной, включая ненулевые зарезервированные биты.
>
> Какая из двух схем используется настоящим PSP-кодом — **не проверено**:
> для этого нужен реальный образ. Обе поддержаны.

## 6. LWL / LWR / SWL / SWR при little-endian

Эталон — QEMU, `target/mips/tcg/translate.c`:

```c
static void gen_lxl(...) {              // LWL
    int sizem1 = memop_size(mop) - 1;    // 3 для слова
    t1 = addr & 3;
    if (!disas_is_bigendian(ctx)) t1 ^= 3;   // t1 = 3 - n
    t1 <<= 3;                                 // сдвиг
    t0 = addr & ~3;
    t0 = load32(t0);                          // memword
    t0 <<= t1;
    t1 = -1 << t1;
    reg = t0 | (reg & ~t1);
}
```

Обозначения: `W = A & ~3`, `n = A & 3`, `b[k]` — байт по адресу `W+k`
(little-endian: `b[0]` — младший байт).

| Инструкция | Раскладка | Диапазон |
|-------------|-----------|----------|
| `LWL` | `rt[3 - n + p] = b[p]` | `p = 0..n` |
| `LWR` | `rt[p] = b[n + p]` | `p = 0..3-n` |
| `SWL` | `b[p] = rt[3 - n + p]` | `p = 0..n` |
| `SWR` | `b[n + p] = rt[p]` | `p = 0..3-n` |

Равносильная сдвиговая форма QEMU для LWL:
`rt = (memword << ((3-n)*8)) | (rt & ~(0xFFFFFFFF << ((3-n)*8)))`.

Побочное подтверждение из `Core/MIPS/MIPSAnalyst.cpp` (`OpWouldChangeMemory`):
маска изменяемых байтов регистра равна `0xFFFFFFFF >> (24 - 8n)` для SWL
(при `n = 0` — только 1 байт) и `0xFFFFFFFF << (8n)` для SWR.

Следствие, важное для проверок: на выровненном адресе **выравненная 32-битная
запись делается одной `SWR`**; `SWL` при `n = 0` пишет только старший байт
регистра в первый байт слова. Round-trip `LWL`+`LWR` как критерий корректности
непригоден — он проходит и при перевёрнутом порядке байтов в каждой из пар.

## 7. PBP

Формат PBP (Little-endian):

```
0x00  magic "\0PBP"
0x04  version (0x00010000 | 0x00020000)
0x08  offsets[8]   : 0 param.sfo, 1 icon0, 2 icon1, 3 pic0, 4 pic1,
                    5 snd0,     6 data.psp, 7 data.psar
0x28  data.psp size      (v0x100)
0x2C  data.psar size     (v0x200)
```

Смещение `0` означает «секции нет». Часть писателей PBP кладёт на место
отсутствующей секции `0xFFFFFFFF` — это **тоже** «секции нет» и такое значение
**нельзя** использовать как границу буфера.

## 8. Что осталось непроверенным

Ниже — утверждения, которые **нельзя** считать подтверждёнными без реальных
образов. Они не должны выдаваться за проверенные.

* Какая из двух схем кодирования `mfc0`/`mtc0` (биты 25..21 или биты 4..0)
  используется настоящим PSP-кодом. Поддержаны обе.
* Физическое расположение регистров VFPU в обозначениях C/R/M/E
  (строки/столбцы/матрицы). Реализованы только операции размера `.s`, где
  индекс регистра совпадает с S-нумерацией; остальные схемы — переупорядочивание
  тех же 128 регистров и в текущем объёме не проверялись.
* Поведение при `ExcCode`, для которого нет обработчика.
* Всё, что касается MMU/TLB: на PSP используется MMU, в проекте — нет.
